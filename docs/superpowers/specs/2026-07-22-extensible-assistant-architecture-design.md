# 可扩展虚拟助手架构设计

> 状态：用户已批准
>
> 日期：2026-07-22
>
> 适用范围：大模型、QQ、电脑控制、Live2D、语音与主动互动的长期演进

## 1. 背景

项目当前采用 Electron + FastAPI：Electron 负责透明桌面窗口、用户交互和 Live2D 渲染，FastAPI 负责系统监控、场景判断、语音合成和消息分发。现有结构可以支撑本机演示型 MVP，但 `MessageRouter` 同时承担消息类型判断、回复生成、TTS 调用和 WebSocket 广播。继续直接加入大模型、QQ 和电脑控制后，该模块会成为难以测试和替换的集中耦合点。

本设计保留现有技术栈，将后端演进为模块化单体（Modular Monolith）。核心能力通过稳定接缝连接具体适配器，为未来更换大模型、QQ 实现、存储方式和操作系统工具保留扩展空间，但暂不引入微服务和通用插件框架。

## 2. 已确认的决策

1. 桌面端继续使用 Electron，Live2D 使用官方 Cubism SDK for Web。
2. 后端继续使用 Python + FastAPI，优先采用模块化单体。
3. 核心业务不直接依赖 Electron、QQ、具体大模型或操作系统 API。
4. 低风险电脑操作可以自动执行，高风险操作必须经用户确认。
5. 每次工具执行都必须支持超时、取消、结果记录和审计。
6. 使用进程内事件分发完成第一阶段，不提前引入 Kafka、RabbitMQ 或 Redis。
7. 持久化优先使用 SQLite；需要语义检索时再增加向量索引。
8. 适合独立部署、无 GUI 且依赖复杂的服务可以使用 Docker；桌面窗口和本机电脑控制不进入容器。
9. 开发过程按可验证阶段提交 Git，最终通过功能分支和 Pull Request 合并到目标仓库。
10. 最终发行 Windows `.exe` 和 macOS `.dmg` 安装包，普通用户不需要预装 Python、Node.js 或 Docker。

## 3. 目标与非目标

### 3.1 目标

- 接入云端或本地大模型时，不修改渠道和 Live2D 实现。
- 增加 QQ 等消息渠道时，不复制对话、记忆和工具逻辑。
- 增加电脑控制工具时，统一经过权限策略和审计流程。
- 不同 Live2D 模型可以通过能力映射复用同一套情绪和动作语义。
- 核心模块可以使用内存适配器独立测试，不依赖 Electron、QQ 或真实模型服务。
- 单项能力失败时可以降级，不拖垮整个助手运行时。

### 3.2 非目标

- 第一阶段不实现通用第三方插件市场。
- 第一阶段不拆分微服务，不引入分布式消息队列。
- 第一阶段不允许大模型直接执行任意 Shell 命令。
- 第一阶段不实现多用户云端部署和跨设备同步。
- 不将 Electron、Live2D 渲染或操作系统 GUI 自动化容器化。

## 4. 总体架构

```text
┌────────────────── 输入适配器 ──────────────────┐
│ Electron 桌面端 │ QQ / OneBot │ 系统事件 │ 定时任务 │
└─────────────────────┬─────────────────────────┘
                      ▼
               统一消息与会话模块
                      ▼
                Assistant Core
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       对话编排      场景规则      记忆管理
          ▼
        模型网关
   云端 LLM / 本地 LLM / 测试替身
          ▼
     工具决策与权限策略
          ▼
  ┌────────────┬────────────┬────────────┐
  │电脑控制工具│系统查询工具│渠道发送工具│
  └────────────┴────────────┴────────────┘
          ▼
        统一响应
  文字 + TTS + 表情 + 动作 + 工具结果
          ▼
  Electron / Live2D、QQ 等输出适配器
```

系统按「输入标准化 → 会话编排 → 模型或规则决策 → 权限判定 → 工具执行 → 响应呈现」流转。适配器只负责协议转换，业务决策集中在核心模块。

## 5. 模块边界

建议逐步形成以下后端目录，而不是一次性搬动所有文件：

```text
backend/
├── api/                    # FastAPI HTTP 与 WebSocket 入口
├── application/            # 用例编排，不包含外部协议细节
│   ├── assistant.py        # 单次对话与工具循环
│   ├── sessions.py         # 会话生命周期
│   └── events.py           # 进程内事件分发
├── domain/                 # 稳定的内部数据模型和业务规则
│   ├── messages.py
│   ├── responses.py
│   ├── tools.py
│   └── permissions.py
├── llm/                    # 大模型网关及具体适配器
├── memory/                 # 会话、短期记忆和长期记忆
├── tools/                  # 电脑控制与系统工具
├── channels/               # Desktop、QQ 等渠道适配器
├── avatar/                 # 情绪与 Live2D 动作语义
├── speech/                 # TTS、后续 STT 和音频处理
├── scenarios/              # 主动场景检测
├── infrastructure/         # SQLite、配置、日志和密钥加载
└── agent/                  # macOS / Windows 系统观测适配器
```

### 5.1 统一消息模块

所有输入转换为受 Pydantic 校验的内部消息，至少包含：

- `message_id`：全局唯一标识。
- `source`：`desktop`、`qq`、`scenario` 或 `system`。
- `conversation_id`：会话标识。
- `sender`：发送者与渠道身份。
- `content`：规范化文本或结构化事件。
- `timestamp`：带时区时间。
- `metadata`：经过限制的渠道附加信息。

该模块是渠道与核心之间的接口。QQ 消息格式、WebSocket JSON 和系统事件都不能越过该边界直接进入对话编排。

### 5.2 对话编排模块

对话编排负责一次完整处理流程：加载会话、读取记忆、调用模型、处理工具请求、生成最终响应并发布事件。它不负责具体网络请求、数据库语句或系统操作。

删除该模块后，复杂流程会重新散落到各个渠道和 API 调用者中，因此它应成为具有高杠杆和高局部性的深模块。

### 5.3 大模型网关

大模型网关提供稳定接缝，隐藏以下实现差异：

- 云端 API 与本地推理服务。
- 流式和非流式输出。
- Tool Calling 格式差异。
- 超时、重试、限流和降级。
- Token 用量和调用成本统计。

至少在存在两个真实适配器时才固化通用能力：例如一个云端模型适配器和一个本地 OpenAI 兼容适配器。测试替身不作为业务适配器数量的依据。

### 5.4 记忆模块

记忆分为 3 层：

1. 当前上下文：本次会话最近消息，由编排模块按预算裁剪。
2. 会话摘要：周期性压缩长对话，保存在 SQLite。
3. 长期记忆：只保存经过筛选的事实和偏好；后续可增加向量检索适配器。

模型不能不经规则直接永久写入记忆。用户应能查看、修改和删除长期记忆。

### 5.5 渠道模块

Desktop 和 QQ 是统一消息接口两侧的适配器：

- 输入方向：将渠道事件转换为内部消息。
- 输出方向：将统一响应转换为渠道支持的文本、语音或动作。
- 渠道连接、重连、限速和协议错误保留在适配器内部。

QQ 首期可以通过 OneBot 11 兼容实现接入，但核心模块不依赖 NapCatQQ、Lagrange 或具体 QQ 客户端名称。

### 5.6 角色表现模块

核心响应使用语义化角色提示，例如：

- `emotion=happy`
- `intent=greet`
- `intensity=0.7`

角色表现模块再根据当前 Live2D 模型能力，将语义映射为真实存在的 expression、motion 和参数变化。模型缺少指定动作时，应降级到兼容的待机或通用动作，不能让业务层感知模型文件名。

### 5.7 工具执行模块

每个工具声明名称、用途、参数模型、风险等级、超时、支持平台和执行结果模型。工具注册表只暴露已批准工具，不接受模型临时拼接命令。

工具模块按能力拆分，例如：

- 系统查询：CPU、内存、当前应用、时间。
- 应用操作：打开应用、切换窗口。
- 输入控制：鼠标、键盘、剪贴板。
- 文件操作：读取、创建、移动或删除受限文件。
- 渠道操作：发送 QQ 消息或桌面通知。

文件删除、发送外部消息、键盘输入、Shell 执行、关闭程序和涉及凭据的操作默认属于高风险。只读系统查询等明确无副作用的操作可以归类为低风险。

## 6. 权限与电脑控制

固定执行链如下：

```text
模型提出 ToolRequest
        ↓
工具是否存在、参数是否合法
        ↓
策略引擎计算风险等级
        ├── 低风险：自动执行
        └── 高风险：创建确认请求
                         ↓
                 Electron 展示影响范围
                         ↓
                批准 / 拒绝 / 超时
                         ↓
                    执行或终止
                         ↓
              记录 ToolResult 与审计事件
```

安全约束：

- 风险由本地策略计算，不能相信大模型自行声明的风险等级。
- 确认界面必须展示工具名称、关键参数、目标对象和预期副作用。
- 用户批准只对当前请求有效，除非用户明确创建范围有限的持久授权。
- 高风险请求默认超时拒绝。
- 执行前后均记录时间、来源、参数摘要、决策和结果，但不记录密码或完整敏感内容。
- 工具框架必须支持取消请求；每个工具声明自身能否安全取消，不能安全取消的操作必须在确认界面说明。
- 第一阶段不提供通用 Shell 工具，只实现参数受控的专用工具。

## 7. 事件、并发与错误处理

### 7.1 进程内事件

使用带类型的进程内事件连接会话、TTS、Live2D 和渠道输出。事件至少包含 `event_id`、`correlation_id`、类型、时间和负载。第一阶段不保证跨进程持久投递。

### 7.2 并发规则

- 同一会话中的消息按序处理，避免上下文交叉。
- 不同会话可以并发处理。
- 新的用户输入可以取消尚未开始执行的模型生成和语音播放。
- 工具执行使用独立超时，不阻塞场景检测和 WebSocket 心跳。
- Live2D 高优先级动作可以中断低优先级待机动作。

### 7.3 降级策略

- 大模型不可用：返回明确错误，或按配置使用备用模型；不能伪造成功回复。
- TTS 不可用：保留文字和动作响应。
- Live2D 不可用：保留聊天、QQ 和系统工具能力。
- QQ 断线：本地桌面端继续工作，QQ 适配器独立重连。
- 存储失败：停止写入记忆并记录错误，不影响只读系统状态查询。

## 8. 持久化、配置与密钥

SQLite 初期保存以下数据：

- 会话和消息索引。
- 会话摘要与长期记忆。
- 工具确认和审计记录。
- 用户设置、模型映射和授权策略。

API Key、QQ Token 等密钥不写入 YAML、数据库明文字段或 Git。优先使用操作系统密钥链；开发环境允许通过未纳入 Git 的 `.env` 注入。日志必须对 Token、Cookie、路径中的敏感信息和用户隐私内容脱敏。

## 9. Docker 使用边界

### 9.1 适合使用 Docker

- GPT-SoVITS 等依赖复杂、端口明确的语音服务。
- Ollama 等可容器化本地模型推理服务，前提是 GPU 映射和平台支持满足要求。
- 后期独立运行的 QQ / OneBot 网关，前提是所选实现支持容器和稳定登录。
- CI 中的后端测试环境。
- 未来需要独立部署的可选服务，例如向量数据库。

这些服务通过仅监听本机或 Docker 私有网络的 HTTP / WebSocket 接缝与主应用通信，并配置健康检查和固定数据卷。

### 9.2 不适合使用 Docker

- Electron 主进程和透明桌面窗口。
- Live2D WebGL 渲染。
- macOS / Windows 前台窗口监控。
- 键盘、鼠标、剪贴板和应用控制。
- 依赖操作系统密钥链与用户确认弹窗的权限模块。

容器化不是默认要求。只有当它能隔离复杂依赖、提高重复部署能力或便于独立升级时才引入，避免为了形式统一增加桌面端开发成本。

## 10. 发行与安装包

Electron 作为安装包主程序，Python 后端按平台构建为独立 sidecar 可执行文件，并通过 Electron Builder 的 `extraResources` 放入应用资源目录。Electron 启动后端、等待健康检查通过，在应用退出时终止后端进程。

- Windows 使用 NSIS 生成 `.exe` 安装包。
- macOS 生成 `.app` 并封装为 `.dmg`。
- Windows 和 macOS 分别在对应操作系统的 CI Runner 上构建后端与 Electron 产物。
- 生产环境使用随机可用端口和每次启动生成的本地访问令牌，不固定暴露未经鉴权的控制端口。
- 用户模型、记忆数据库、配置和缓存写入系统用户数据目录，不写入签名后的应用资源目录。
- GPT-SoVITS 和大型本地模型作为可选外部服务或独立下载组件，不强制打入主安装包。
- 对外发布前，Windows 产物需要代码签名，macOS 产物需要代码签名和 Apple 公证。

第一阶段只预留后端生命周期和配置接缝，正式打包在核心功能稳定后单独编写发行规格与实施计划。

## 11. 测试策略

### 11.1 单元测试

- 统一消息和响应模型校验。
- 风险分类、确认过期和拒绝路径。
- 对话编排在模型、记忆和工具测试替身下的行为。
- Live2D 语义到模型动作的映射与降级。
- 会话裁剪、摘要和长期记忆写入规则。

### 11.2 契约测试

- 每个大模型适配器满足同一网关契约。
- Desktop 和 QQ 适配器满足统一渠道契约。
- macOS 和 Windows 工具返回相同的结果模型。

### 11.3 集成测试

- Desktop 消息经过模型生成响应并推送到 WebSocket。
- 模型提出低风险工具后自动执行并返回结果。
- 模型提出高风险工具后暂停，获得批准才执行。
- QQ 消息与桌面消息共享会话、记忆和业务规则。
- TTS 或 Live2D 故障时仍能输出文本结果。

### 11.4 端到端测试

- Electron 与 FastAPI 的启动、重连和退出。
- Live2D 模型加载、动作、口型和点击互动。
- 高风险确认界面完整展示并正确回传决定。
- Docker 可选服务启动后的健康检查和主应用连接。

## 12. 分阶段实施与 Git 检查点

每个阶段都必须通过对应测试和 `git diff --check` 后再提交；提交只包含该阶段相关文件。

1. **现有加固基线**：验证并提交当前 FastAPI 重构、Electron 安全加固、TTS、场景和 CI 改动。
2. **领域模型与消息边界**：加入统一消息、响应、事件和会话标识，迁移现有 API 与 WebSocket。
3. **对话编排与模型网关**：接入一个可配置模型适配器和测试替身，保留后续本地模型接缝。
4. **SQLite 会话与记忆**：实现短期上下文、摘要存储和可管理的长期记忆。
5. **工具与权限框架**：实现注册表、风险策略、确认状态机、审计和少量低风险工具。
6. **Live2D 正式运行时**：接入官方 Cubism SDK，实现动作状态、表情映射、物理、口型和点击互动。
7. **QQ 渠道适配器**：接入 OneBot 兼容实现，增加身份、群聊范围、限速和断线重连。
8. **主动互动和 Docker 配套**：统一系统事件、定时任务，按实际选择增加 Compose 配置和健康检查。
9. **安装包与发布验收**：实现后端 sidecar 生命周期和双平台构建，执行完整测试、签名配置与安全检查，推送功能分支并创建 Pull Request。

推荐提交遵循单一目的，例如：

```text
docs: 记录可扩展助手架构设计
refactor: 建立统一消息与响应模型
feat: 增加可替换的大模型网关
feat: 增加工具权限与确认流程
feat: 接入 Live2D Cubism 运行时
feat: 增加 OneBot QQ 渠道适配器
```

## 13. 验收标准

- 新增一个模型适配器不需要修改渠道、记忆和 Live2D 模块。
- 新增一个消息渠道不需要复制对话、工具和权限逻辑。
- 低风险工具可以自动执行，高风险工具未经确认绝不执行。
- 每次工具请求都能通过 `correlation_id` 追踪到输入、确认和结果。
- Electron、QQ、TTS 或 Live2D 任一适配器故障不会导致其他能力全部停止。
- 自动化测试覆盖高风险批准、拒绝、超时和取消路径。
- Docker 服务不是运行桌面助手的强制依赖；未启用可选容器时核心应用仍可启动。
- Windows 和 macOS 安装包可在未安装 Python、Node.js 和 Docker 的干净系统中启动核心应用。
- 每个实施阶段均有独立、可回退且已验证的 Git 提交。
- 最终改动通过功能分支推送到 `frewily/Virtual-Anime-Assistant-Long-term-project-`，经 Pull Request 审查后再合并。

## 14. 后续规格拆分

总体设计批准后，不用一个超大计划同时实现全部能力。按以下顺序分别编写规格和实施计划：

1. 统一消息、会话和对话编排基础。
2. 大模型网关与 SQLite 记忆。
3. 工具权限、确认和电脑控制。
4. Live2D 正式运行时。
5. QQ / OneBot 渠道。
6. 主动互动与可选 Docker 服务。
7. Windows `.exe`、macOS `.dmg` 与发布流水线。

第一份实施计划只覆盖第 1 项，完成并验证后再进入下一项，避免同时修改多个核心接缝。
