# 云端 QQ 助手部署设计

## 1. 背景与目标

Virtual Anime Assistant（以下简称 VAA）目前已具备 Web 设置、OneBot QQ 渠道、SQLite 会话与记忆、工具调用及模型回复能力。本设计将 QQ 助手部署到用户现有的阿里云轻量服务器，使其在本地电脑关机后仍能全天在线。

第一版仅供用户个人使用，聚焦 QQ 消息处理，不将桌面交互能力整体迁移到云端。

成功标准如下：

- 专用 QQ 小号可以全天接收消息并通过模型回复。
- 云端聊天记录、记忆和配置独立于本地环境。
- 管理页面与服务接口不暴露到公网。
- 不占用公网 80、443 端口，不修改宝塔 Nginx、个人网站或博客。
- 服务器或容器重启后，服务能够自动恢复。
- 合并到 `main` 的通过测试版本可以自动部署，并可在健康检查失败时回滚。

## 2. 范围

### 2.1 第一版包含

- 云端 VAA 后端。
- NapCat QQ 客户端及 OneBot 通信。
- 云端独立 SQLite 会话、记忆与配置。
- 通过 SSH 隧道访问 VAA 设置页和 NapCat 管理页。
- Docker Compose 编排、资源限制、健康检查、日志轮转和自动重启。
- GitHub Actions 自动部署与失败回滚。
- SQLite 定时备份。

### 2.2 第一版不包含

- Live2D、桌面窗口与本地交互界面。
- 本地大语言模型。
- GPT-SoVITS 等本地语音服务。
- 本地与云端的配置、聊天记录或记忆同步。
- 公网 Web 设置页或公网 API。
- 修改现有宝塔 Nginx、网站、博客及其 80、443 端口配置。
- Docker Swarm 或 Kubernetes。

## 3. 运行环境与约束

目标服务器采用 Alibaba Cloud Linux 3，架构为 x86_64，规格为 2 核 CPU、2 GiB 内存和 40 GiB 系统盘。服务器已安装 Docker Compose v2.27.0。

现场只读检查显示：

- 内存总量约 1.8 GiB，可用约 729 MiB。
- 已存在 1 GiB Swap，当前无需扩容。
- 系统盘已使用约 17 GiB，剩余约 22 GiB。
- 当前 `admin` 用户不能直接访问 Docker Socket，部署用户权限需要单独配置。

服务器同时运行宝塔、个人网站和博客。VAA 必须通过资源上限与端口隔离避免干扰现有服务。

## 4. 方案选择

### 4.1 选定方案：完整 QQ 助手云端化

VAA 后端、NapCat 和 SQLite 均在服务器运行。该方案无需依赖本地电脑，能够实现真正的 QQ 全天在线；同时保持本地桌面版与云端 QQ 版数据隔离。

### 4.2 未采用方案

仅将 NapCat 放到云端仍要求本地 VAA 在线，无法满足全天回复目标。将完整设置页与 API 通过 HTTPS 公网开放会增加鉴权、Nginx 和攻击面管理成本，也可能影响现有网站，因此第一版不采用。

## 5. 系统架构

Docker Compose 管理 2 个核心容器：

- `vaa-app`：负责 OneBot 事件处理、模型调用、工具执行、会话、记忆和 SQLite 持久化。
- `napcat`：负责 QQ 小号登录和在线状态，通过 OneBot 与 `vaa-app` 通信。

两个容器加入专用 Docker Bridge 网络。OneBot 事件和动作请求仅在该网络中传输，不映射到公网地址。

VAA 设置页和 NapCat 管理页如需映射主机端口，只能绑定到 `127.0.0.1`。管理员通过 SSH 本地端口转发临时访问，SSH 隧道关闭后外部无法连接。

云端数据使用独立持久化目录或命名卷，包括：

- SQLite 数据库与记忆数据。
- VAA 云端配置。
- NapCat 登录状态和必要配置。
- 备份文件。

部署和版本回滚不得替换或删除这些持久化数据。

## 6. 消息与数据流

1. NapCat 接收 QQ 消息，并通过 Docker 内网发送 OneBot 事件。
2. `vaa-app` 校验 OneBot 鉴权信息，加载该 QQ 会话对应的云端记忆。
3. `vaa-app` 调用已配置的远程模型，并按既有权限状态机执行工具。
4. `vaa-app` 将回复写入云端 SQLite，再通过 OneBot 动作请求交给 NapCat。
5. NapCat 将回复发送到 QQ。

语音功能仅在配置了云端可访问的远程 TTS 时启用。TTS 未配置或暂时失败时，系统退回文字回复，不影响主消息链路。

## 7. 部署与更新

服务器创建专用 `vaa-deploy` 系统用户，部署目录为 `/opt/virtual-anime-assistant`。该用户使用独立 SSH 密钥登录，不使用密码登录。为避免失联，第一版上线期间不立即关闭现有管理员或 root 登录；完成验证后再单独安排 SSH 加固。

部署用户仅获得完成下列操作所需的最小权限：

- 读取部署目录和受限配置。
- 管理本项目的 Docker Compose 服务。
- 运行项目部署、健康检查与回滚脚本。

GitHub Actions 在 `main` 分支测试通过并更新后，通过专用部署密钥连接服务器。流水线执行：

1. 定位目标提交并保留当前可用版本标识。
2. 拉取或同步目标提交。
3. 构建新镜像。
4. 启动或更新容器。
5. 执行应用、OneBot 和配置健康检查。
6. 健康检查成功后记录新版本；失败则恢复上一可用版本。

自动回滚只恢复应用镜像与部署文件，不回滚 SQLite 和 NapCat 持久化数据。部署脚本必须串行化，避免两个工作流并发更新同一实例。

## 8. 密钥与网络安全

模型 API Key、OneBot Token 和其他秘密保存在服务器的权限受限环境文件中。文件不提交 Git，不由 CI 输出，不写入容器镜像。第一版不引入 Docker Swarm Secret，以降低单机部署复杂度。

安全边界如下：

- 公网不开放 VAA 端口、NapCat 管理端口或 OneBot 端口。
- 管理页面仅通过 SSH 隧道访问。
- 不修改宝塔 Nginx 与现有站点配置。
- GitHub Actions 使用独立的最小权限部署密钥。
- Docker 日志不得记录 API Key、密码、Token、环境变量或模型私有推理字段。
- NapCat 首次扫码和掉线后的重新登录均通过 SSH 隧道进行。

## 9. 资源与运行策略

初始资源上限如下：

| 服务 | 内存上限 | CPU 上限 |
| --- | ---: | ---: |
| `vaa-app` | 512 MiB | 0.8 核 |
| `napcat` | 768 MiB | 0.8 核 |

剩余资源留给系统、宝塔、网站和博客。两个容器均使用自动重启策略，但需要设置合理的健康检查间隔与重试阈值，避免持续故障时形成高频重启循环。

现有 1 GiB Swap 继续保留。只有在实际运行监控表明内存不足时，才另行评估扩容 Swap 或服务器规格。

Docker 日志采用大小和文件数量双重限制。SQLite 备份同样设置保留数量，防止占满系统盘。

## 10. 故障处理与恢复

- **模型服务异常：** 采用有限次数、带退避的重试；达到上限后返回简短错误消息，不无限重试。
- **TTS 异常：** 自动退回文字回复。
- **OneBot 断连：** `vaa-app` 保持运行并等待重连；NapCat 按重启策略恢复。
- **QQ 登录失效：** 保留必要日志，由管理员通过 SSH 隧道进入 NapCat 管理页重新登录。
- **应用健康检查失败：** 自动部署恢复上一可用应用版本，不覆盖持久化数据。
- **容器或服务器重启：** Docker 自动启动服务，SQLite 与 NapCat 状态从持久化卷恢复。
- **磁盘空间紧张：** 日志轮转与备份保留策略先行控制；达到告警阈值时停止生成非必要备份并提示人工处理。

## 11. 备份策略

SQLite 使用数据库一致性备份方式定时生成副本，不直接复制正在写入的数据库文件。备份保存在部署数据目录的独立子目录，并按固定数量轮转。

首版默认每天备份 1 次，保留最近 7 份。部署前额外创建 1 份备份。恢复操作必须由管理员显式执行，自动回滚不得自动恢复数据库，以避免覆盖部署后产生的新消息。

## 12. 健康检查与验收

### 12.1 自动化验证

- 配置加载与秘密缺失时的失败行为。
- OneBot 鉴权和内部连接。
- QQ 事件到模型回复的消息处理链路。
- SQLite 会话与记忆持久化。
- 健康检查返回值。
- 部署失败后的应用版本回滚。

### 12.2 上线验收

- QQ 文本消息可以连续收发，且多轮上下文有效。
- 已授权工具可以通过真实 QQ 对话调用。
- 未配置或故障的 TTS 不阻断文字回复。
- 单独重启 `vaa-app`、NapCat 以及整台服务器后服务均能恢复。
- QQ 掉线后可以通过 SSH 隧道重新登录。
- 从公网无法访问 VAA、NapCat 和 OneBot 管理端口。
- 自动部署成功时切换到新版本，健康检查失败时恢复上一版本。
- SQLite 数据在应用更新和回滚后保持完整。
- 部署前后个人网站与博客均可正常访问，现有 80、443 端口和宝塔配置未变化。

## 13. 实施顺序

1. 补齐云端运行所需的配置分层、容器构建与健康检查。
2. 增加 Docker Compose 云端编排、资源限制、日志轮转与持久化卷。
3. 增加部署、备份、健康检查和回滚脚本。
4. 增加 GitHub Actions 自动部署工作流及相关测试。
5. 在服务器创建专用用户、目录和受限密钥文件。
6. 首次部署 VAA 与 NapCat，通过 SSH 隧道完成 QQ 扫码和模型设置。
7. 执行完整上线验收，并观察资源占用与现有网站状态。
